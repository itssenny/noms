# noms architecture

- Frontend: responsive vanilla JavaScript SPA. `app.js` renders product surfaces; `ingredients.js` owns catalogue search, selection, and shared unit options.
- Backend and authentication: Supabase PostgreSQL and Supabase Auth through `supabase-client.js`. Browser configuration uses a publishable key, never a service-role key. The Ruby build supports public configuration from environment variables or `supabase-config.local.js`.
- Source of truth: `db/supabase/001` through `023`. `db/schema.sql` is a legacy SQLite/D1 design and is not used by the current browser persistence layer. Existing hosting D1 metadata is retained, not migrated.
- Shared catalogue: `ingredients.id` is referenced by `inventory.ingredient_id` and `recipe_ingredients.ingredient_id`. Authenticated users read shared starter records and their own custom records. Migration 007 enables owner-only custom creation/editing; shared rows remain protected. The picker supports inline creation, and Inventory → Manage ingredients provides a catalogue editor. Names are presentation data; IDs are persisted identity.
- Inventory: one record per user and ingredient. RLS restricts all operations to its owner. Quantity, entered unit, storage location, threshold, expiry and notes belong to inventory. Default units belong to the catalogue and are suggestions only.
- Profiles and recipes: migration 023 separates public profiles from Auth users. `recipes.user_id` now references a profile ID for compatibility; `profile_memberships` maps authenticated managers to personal or official profiles and all recipe/ingredient RLS checks membership. Regular users receive one personal profile. The official public `@noms` profile has no Auth identity; a database operator grants its initial owner membership using the UUID-specific SQL comment at the end of 023. Recipe edits remain atomic through `update_recipe`; the editor scopes recipes to the selected profile while pantry and authentication remain user-scoped.
- Units: entered units are preserved. Cooking compares matching ingredient IDs and converts g/kg, ml/l and piece/pcs; incompatible units require manual review. Recipe, shopping and inventory quantities are optional. NULL inventory quantity means present with an unspecified amount; it never becomes zero or triggers an automatic deduction.
- Legacy limitations: inventory display state remains name-keyed; cooking matches stable IDs when available. Planner/shopping state is in localStorage under per-user keys; it does not sync across devices. Unowned legacy shared state is preserved but not automatically assigned to any account. Account changes clear rendered kitchen state and stale database loads are ignored. Recipes/inventory are stored in Supabase under RLS.

See `db/CANONICAL_INGREDIENTS.md` for rollout, data review and validation.

Colour atelier presentation: `atelier.css` layers the approved white/black/orchid/pink/citron theme over the existing component styles. Local outline icons are supplied by `ui.js`; no icon CDN is required. Home's featured recipe, weekly menu ("Make a date."), and low-stock card render real account state with explicit empty states. Recipe covers use user images; missing covers get an illustrated placeholder rather than unrelated stock photos.

Meal planning now stores a local calendar date per entry and supports browsing previous/future weeks. Legacy weekday-only plans are assigned to the current week once on read and persisted immediately; historical meals are not inferred. `planning.mjs` owns date keys, shopping coverage/top-ups and stable recipe-source IDs. Shopping review shows all ingredients, with inventory shortages checked by default, manual overrides and an explicit add-to-shopping action. Shopping recipe labels can be hidden per account and are cleared independently of quantities when recipes are deleted or their final planned meal is removed. These planner/shopping records remain per-account browser storage, not cloud-synced.

Optional recipe amounts require migration 008. A NULL ingredient quantity means As needed; unit `to taste` distinguishes that label. Such rows use inventory presence for readiness, never scale numerically, and are excluded from automatic stock deduction. Derived shopping items retain NULL quantities instead of inventing units. Inventory quantities use NULL for present with an unspecified amount, zero for out of stock, and positive values for precise tracking; migration 012 enables this alongside optional receipt quantities. Ingredient creation is available within typed search results; repeated per-row add buttons are removed. Shopping completion uses a dedicated 32px checkbox, while recipe-source buttons open a native dialog without toggling the item.

Post-cook inventory check-in: tracked ingredients offer leave unchanged, still have some (amount unknown), used it up, or set an exact amount. Where a numeric remainder can be calculated, that exact value remains the default; unknown or flexible quantities do not require a calculation. These choices reuse the existing NULL/zero/positive inventory values and need no schema migration. The optional rating and note prompt follows the inventory check-in or its skip action.

Ingredient substitutions: migration `009_ingredient_substitutions.sql` adds explicit directional 1:1 rules, shared starters and account-owned custom rules. Catalogue → Ingredient substitutions manages custom rules. Stock checks offer only positive-stock alternatives linked by ingredient IDs; they never infer similarity from names. Users choose a replacement in recipe details or the meal planner. Each planned meal stores its choices with the existing per-account local planner state. Cooking uses that meal snapshot and deducts the selected stock item after the usual final confirmation. Unit conversions remain dimension-safe; stock reserved by another ingredient cannot be counted twice. Unknown quantities never auto-deduct. Missing migration 009 leaves ordinary kitchen loading usable and shows setup guidance in the catalogue. Session-only recipe-detail choices clear on account changes. Rules sync through Supabase; meal plans retain the existing browser-local persistence.

Planner interactions: day view supports moving an existing meal by native drag/drop; the optional meal-slot view shows Breakfast, Lunch, Dinner and Snack (existing Brunch entries appear under Lunch, retaining their Brunch label until moved). Dropping on a week-navigation button moves the meal seven days and opens that week. Moves preserve meal IDs, servings, substitutions and all shopping entries, and roll back on storage failure. Move / edit provides the date-and-slot alternative for keyboard/touch users. The slot-view preference is browser-local and scoped to the signed-in account.

Duplicate meal opens a new meal draft for the next date; Plan leftovers opens the same draft marked already cooked and linked via leftoverOf to its source meal. Leftovers persist isLeftover, never add shopping ingredients (including stale form selections), and offer View recipe rather than Start cooking, preventing a second deduction. Marking a previously planned meal as leftovers leaves any shopping entries already added untouched. No extra database migration is needed: these fields live with the existing per-account local planner state.

Planner gallery: all generic add-meal entry points open a photo/name recipe picker with Highest rated, Recently cooked (last 30 days), It's been a while (older history), Not cooked yet, and All recipes shelves. Search, ready-to-cook, 30-minute and cuisine/tag filters apply to every shelf. Selection retains the clicked date and slot; changing a recipe inside a draft preserves date, slot and servings and recalculates ingredient needs. Planner cards display only the cover/name, Move / edit, More and a leftover marker when applicable; cooking/duplicate actions live under More.

Cooking history is explicit and private per signed-in user (migration `035_recipe_made_checkins.sql`). Finishing the stepper never records completion. The feedback popup after the ingredient check-in and the full recipe page offer Made it; the dialog can mark or unmark any accessible recipe, including unsaved recipes, with optional rating, private note and public comment. The check-in RPC saves these atomically and supports stable note/comment IDs for retries. `recipe_made` has author-only RLS; `get_recipe_made` and `get_made_recipes` enforce current recipe access. Profile What I made reads this history independently of Created/Saved and shows only the current user's optional feedback. Legacy automatic `recipes.last_cooked_at` values are preserved in storage but deliberately not imported or counted. Inventory updates remain independent.

Recipe shopping and feedback: recipe details expose a standalone inventory-aware shopping review. Its shopping-only submission uses the existing selected-ingredient top-up and recipe-source logic, with rollback on persistence failure; it never creates or changes meal plans. Servings and explicit substitutions are carried over from recipe detail, and users may override the default missing/stocked selections.

Personal recipe feedback: migration `010_recipe_note_posts.sql` stores private timestamped posts in recipe_notes. The owner-scoped save_recipe_feedback RPC saves a rating and optional new note atomically; per-draft note IDs make retries idempotent. Migration 010 copies legacy recipes.notes into one earlier post with an unknown date and clears the old field only after copying. Re-running the migration does not recreate deleted legacy posts. Recipe editing preserves ratings and posts, and recipe deletion cascades to its posts. Failed saves retain the draft, optional blank post-cook fields preserve existing data, and stale account/load responses cannot overwrite a newer feed. Labels progress from minutes/hours to one day, weekday, and a date; the full timestamp is available on the time element. Missing setup leaves the kitchen usable and shows an actionable message.

Shopping shortcuts: Often bought is a searchable pinned-ingredient panel beside the shopping list. Pins use per-account browser-local storage, matching the planner's current local persistence, and do not add purchases until the user chooses the cart action. Inventory rows expose the same quantity/unit shopping dialog. Independent additions preserve existing recipe labels, merge compatible units or legacy name-only entries, and never change meal plans or inventory. Pin removal leaves shopping untouched. The direct recipe-shopping checklist has a Select all / Unselect all control that tracks manual checkbox changes and retains overrides when servings change.

Shopping → inventory: checking and unchecking only persist bought status locally. “Add all checked items to inventory” transfers checked food items sequentially, retaining list rows and marking received purchases. Non-food entries are excluded. Migration 011 provides owner-scoped shopping_receipts and category overrides; migration 012 permits NULL quantities in inventory/receipts and updates receive_shopping_item. Known amounts use compatible-unit conversions; combining any unspecified amount leaves the total unspecified. Catalogue ambiguity or incompatible units opens confirmation. Locally persisted receipt IDs/payloads make retries safe after lost responses; repeated check-offs cannot transfer settled purchases again. Existing location/category/threshold are retained. Account switches ignore stale responses.

Inventory editing changes the current user's location/category override without altering shared catalogue ingredients. Category dots use a consistent palette, with deterministic colours for custom categories. Inventory filtering combines search/location with stock-first, low/out-first or name sorting. Recipe filtering combines search, readiness, difficulty and tags, with two-direction time/rating/difficulty/name sorting. Filter choices persist for the current session and clear on account switches. Recipe details opened from planner cards return to the selected planner week instead of the recipe database; cooking exits preserve that origin.

Mixed shopping entry: Add item offers a free-text item mode and a catalogue ingredient mode. Free-text entries default to inventoryMode=skip and can be completed without catalogue lookup or inventory writes; the user may explicitly enable food inventory tracking. Catalogue entries follow the existing quantity/unit purchase intake. Shopping-only entries are excluded from recipe coverage and ingredient merging. Older unlinked shopping entries can also be completed via Just mark purchased in the purchase confirmation. Per-mode unit drafts are retained when switching input modes. No new database migration is required.

Catalogue add/edit now uses a native modal dialog with Save/Cancel and Escape handling; account reset removes it. Its submit handler checks the form's id attribute rather than form.id, which may be shadowed by the hidden ingredient ID control. Substitution settings use a visually distinct panel, separate from the ingredient search/list section. Global select styling uses pill shapes and native customizable picker styling where supported, retaining native keyboard/touch fallback. Clickable controls receive subtle hover feedback, with reduced-motion preferences respected.

Recipe tag catalogue: migration 013 creates shared recipe_tags for signed-in users, seeded by cuisine, diet, meal and style. Migration 014 lets signed-in users contribute custom tags as shared “Other” entries; clients cannot edit or delete catalogue rows. Recipes retain their tag arrays, and the editor displays all selected tags in cards, details and previews. Typed tags are added to the catalogue when committed as chips. The recipe editor loads up to 500 catalogue tags on opening; unavailable setup leaves typed tags on the recipe and shows a setup message.

Planner recipe cards open the same native preview dialog as shopping recipe labels. Open full recipe preserves the return destination. Custom and native dialogs use 240ms entry transitions; native dialogs and explicit custom close actions fade out. Reduced-motion preference disables the transitions.

Personal category colours: migration 015 creates category_colour_preferences keyed by user/category with owner-only read/write policies and validated hex values. category-colours.js loads preferences with the kitchen, guards late account responses and saves them from Manage ingredients. list-models.mjs supplies one palette to the catalogue, inventory, shopping, recipe ingredients and home top-up dots; account changes clear overrides. Default-colour changes remain drafts until saved. Setup failures leave the default palette usable with a setup message in Manage ingredients.

Header photo: profile.js owns the avatar, loading it at sign-in rather than only when the profile opens. Same-account auth refreshes preserve it; sign-out/account switches clear it and stale profile reads/saves are ignored. auth.js only controls sign-in visibility/email. The visible product name is noms. Existing storage keys and internal mise-prefixed events remain stable to preserve local planner/shopping data.


Profile and recipe privacy (migration 016): extend the existing profiles with is_private (default true), show_diet and show_cooking_level (both default false); extend recipes with visibility (default private). All existing records retain identity and become explicitly private. Public recipe access requires both visibility=public and a public creator profile; owner access remains independent of those settings.

The existing owner-only recipes/profiles/recipe_ingredients policies remain intact. This is intentional: recipes also contains private rating, notes and last_cooked_at fields, so granting public row SELECT would leak personal data. Authenticated visitor RPCs get_visible_profile, get_visible_recipe and get_profile_recipes instead return whitelisted, masked JSON. Internal recipe_public_document is not executable by clients. Custom ingredient IDs and recipe-facing names are included only inside an authorized recipe; the ingredient catalogue and its write policies remain unchanged. No duplicate ingredients are created.

saved_recipes is a user/recipe UUID junction with a composite primary key and cascading deletion. RLS permits reading/removing only one's own saves and inserting only accessible recipes owned by someone else. get_saved_recipes rechecks original access on every query and returns a null recipe for an inaccessible bookmark, preserving the relationship for later restoration without leaking its name, author or cover. Deleting the original removes the bookmark through its foreign key. Saved records are loaded separately and never counted as Created. The planner can use accessible saved recipes, retaining the existing local account storage and shared ingredient IDs. Another person's private custom ingredient is not added to the viewer's ingredient catalogue; receiving shopping stock for it may require selecting an ingredient from the viewer's own catalogue.

Recipe covers: migration 016 makes recipe-covers private without moving/deleting objects or rewriting legacy URLs. The frontend resolves existing public URL values to storage paths, performs authenticated downloads under storage RLS, and renders browser-local blob URLs. New uploads store paths. Storage checks match both the original recipe ownership and its current accessibility, preventing a forged recipe from exposing somebody else's cover. Avatars retain their existing public behavior because avatar/username are the permitted minimal private-profile identity. Already downloaded content cannot be retracted.

Profile URLs use #/profile/<username-or-uuid>; recipe URLs use #/recipe/<uuid>, within the existing signed-in shell. Access requires sign-in. Migration 020 adds a filtered Discover feed for public recipes and shared starters. Profile owners see all Created recipes and editing links; visitors see the filtered profile and accessible recipes. My Recipes offers Created and Saved subpages. Notes, ratings and cooking-history writes remain owner-only, with no shared feedback UI. Saved access is revalidated on library entry, direct recipe opening, sign-in and window focus. The database/API always enforces current access, independent of cached UI.

### Pantry tracking (019)

`inventory.is_active` belongs to each user's inventory record; the shared catalogue and recipe references are unchanged. Existing records default to active. Inactive rows must have a known quantity of zero. The database rejects deactivation of positive or unknown quantities. A quantity update that restocks an inactive row reactivates it; receipt replays do not update stock or membership. Manual additions upsert the existing user/ingredient key with active membership, including when the added quantity is zero.

Inventory defaults to active rows. Stock summary cards are toggleable stock filters and compose with search, location, and sort. The tracking selector exposes Active, Inactive and All; changing tracking clears the stock filter. Out of stock shows the count of active, out-of-stock ingredients only, regardless of the selected tracking view. The existing stock editor offers Mark as Inactive or Reactivate. Inactive records remain available for catalogue search, recipe references and shopping additions, while readiness, stock reminders and automatic low-stock shopping exclude them. `cooking.mjs` defensively treats inactive stock as unavailable even if passed inconsistent client data.

Apply `db/supabase/019_inventory_tracking.sql` after earlier migrations before deploying this version. Inventory owner RLS and the existing unique key continue to enforce private, duplicate-free tracking.

Post-cooking reconciliation includes “Used it up — mark inactive” alongside “Used it up — keep active.” The inactive option writes quantity zero and `is_active=false` in the same inventory upsert, retaining the ingredient key, unit, location and threshold. Other stock additions reactivate by default; reconciliation explicitly preserves inactive membership when keeping an already inactive ingredient empty. Completion writes are scoped to the initiating account and stale results do not replace another account's client inventory. This uses migration 019; no additional schema change is required.

Recipe deletion is now inside a closed Recipe options menu, separate from Start cooking. Start dispatch was verified in the user's Safari session and in an isolated browser fixture; the reported delete prompt on a cooking click was not reproduced, so no hardware/pointer cause has been established.


### Shared starter recipes and website import (020–021)

Migration 020 extends the existing recipes table with catalog_key and a nullable owner only for operator-seeded public catalogue rows. A check constraint and unchanged owner RLS prevent clients from creating or claiming starters. Visitor/saved projections continue to whitelist fields; ratings, notes and cooking history stay private. Migration 021 seeds three original noms recipes and references existing shared ingredient IDs by normalized name, inserting shared ingredients only when absent. Both migrations are transactional and rerunnable; seeds never overwrite existing catalogue recipes. Starters appear in Discover, then in Saved when bookmarked; they never become Created recipes.

Six-character share_code values are database-generated on the first visibility=public insert/update. Private drafts have no code. Codes are unique, cannot be chosen/replaced by clients, and persist through private/public toggles. A code is an identifier, not access permission: lookup/discovery still requires a public recipe and public author profile (or an operator-seeded starter). Existing public recipes receive their first code when 020 is applied. The details page copies the code; Discover accepts codes without case sensitivity; #/recipe/CODE also resolves through the authorized lookup. Existing UUID links remain valid.

The recipe-import Supabase Edge Function checks the signed-in user with Auth before network access. It fetches public HTTPS recipe pages with per-hop URL/DNS validation, pins the IPv4 connection and verifies TLS against the original hostname, and bounds redirects, time, headers and response size. Deno's native TCP/TLS APIs are used because its node:https implementation does not support custom lookup. Structured JSON-LD Recipe nodes are read without executing site scripts. Multiple recipes offer a choice; HowToSection instructions are flattened. Unsupported sites, social/video links and missing recipe data leave the URL form available for retry/manual entry. No TikTok/Instagram access, AI transcription, HTML-page guessing or remote image copying is implemented.

Import produces a transient review draft in the existing editor, initially private. Simple explicit quantities/units and exact catalogue names may be prefilled; unresolved ingredients must be chosen using the existing picker. Imports do not automatically create ingredients. Original ingredient lines remain in editable preparation notes, source_url retains the fetched recipe URL, and all recipe fields are editable. Unknown time/servings require user input. Cancel/account changes discard the transient draft and ignore stale results. Saving uses the existing creation flow with compensating deletion on failure (the existing multi-request creation limitation remains); it opens Created recipes. Publishing uses the same editor and database trigger as manual recipes.

See db/RECIPE_CATALOG_ROLLOUT.md for deployment, verification commands and phase-one limits. No hosted database changes or function deployment are performed by the build.
