Metric / US ingredient measurements

Architecture: recipe_ingredients.quantity/unit remain the source of truth, linked to ingredients.id. Servings are calculated by existing recipeChecks; display conversion runs afterward. Inventory deductions, shopping aggregation and recipe ownership retain their existing behavior. The historic SQLite db/schema.sql is not the active Supabase schema.

Apply db/supabase/026_ingredient_measurements.sql, then 027_starter_measurement_densities.sql. These add nullable density_g_per_ml and conversion_metadata to existing canonical ingredient records, plus an exact, RLS-respecting alias lookup function. No separate catalogue, ownership changes or recipe-data backfill. Deployment requires these migrations and the updated recipe-import shared modules. The UI safely uses same-dimension conversions if metadata cannot load.

The starter seed contains 35 ingredients, 28 with documented culinary estimates. Source: https://www.kingarthurbaking.com/learn/ingredient-weight-chart (checked 2026-11-14). Each populated factor stores the original reference amount/unit/grams, source URL, verification status and scope. The complete ingredient list and reference amounts are in migration 027. Fractions of a US cup/spoon use NIST US customary volumes: https://www.nist.gov/pml/owm/si-units-volume . These are bulk cooking estimates, not laboratory physical densities. Sugar uses the source's 198 g/cup; butter uses 113 g/half cup.

Milk, heavy cream, water, generic salt/rice, and unqualified brown/powdered sugar intentionally have no density. Generic liquids still convert ml ↔ US volume safely. Salt crystal size, cooked/dry rice, packing/sifting and brand can change factors substantially. Qualified canonical records distinguish these forms. Notes indicating changed preparation suppress cross-dimension conversion conservatively. conversion_metadata can accommodate future preparation_factors, but those are not automatically selected today.

Existing canonical names are reused exactly; existing records are never merged by name or alias. Curated aliases attach to the canonical record and inherit its density. Ambiguous aliases return multiple candidates and need manual selection. Existing separate alias-named records retain their IDs and need administrator review rather than automatic consolidation. Private ingredients are not seeded or overwritten. Import preserves source units, normalizes supported US/metric spellings, retains raw source lines in notes, and uses exact canonical/alias matches only when unique. Composite expressions with explicit metric totals retain that supplied total; uncertain package sizes remain for review.

Preference uses account-scoped localStorage, matching other local UI settings. It persists across recipes/reloads on the same browser, with Metric as default; cross-device profile synchronization is a future improvement. All display calculations derive from original values, with formatting performed last. US fractions are shown only within 2% of the calculation; otherwise three significant digits avoid misleading snaps. Count/descriptive units stay in their original units (numeric counts still scale with servings).

Validation: node --test tests/measurements.test.mjs; PGLITE_MODULE=/path/to/@electric-sql/pglite/dist/index.js node --test tests/*.test.mjs; npm run build. Migration tests check seed idempotency, canonical alias IDs, preserved recipe data, private catalogue visibility and shared-row write restrictions. Live Supabase deployment and real-account acceptance remain separate from local validation.

Teaspoons and tablespoons are shared display units: source tsp/tbsp amounts and aliases remain spoon measures in both Metric and US, including when a density is available. Servings still scale from the original quantity. Explicit conversions keep the existing US customary factors used by stored recipes; this display change does not reinterpret source volumes or alter saved recipes.
